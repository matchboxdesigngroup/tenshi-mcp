# Git Standards

## Branch Naming

| Prefix | Use |
|---|---|
| `feat/<slug>` | New calculator or user-facing feature |
| `fix/<description>` | Bug fix |
| `chore/<description>` | Build, config, dependency, or tooling change |
| `docs/<description>` | Documentation only |
| `refactor/<description>` | Internal restructure with no behavior change |

Use kebab-case. Keep slugs short and descriptive (`feat/arm-calculator`, not `feat/add-the-new-arm-adjustable-rate-mortgage-calculator`).

## Commit Messages

Follow the **imperative, sentence-case** style used throughout this repo:

```
Add CD calculator core engine
Fix loanAmount rounding in loan-credit-line summary
Register loan-credit-line block in PHP plugin
Extract formatters to shared utils
```

Rules:
- Start with a capital verb: **Add**, **Fix**, **Register**, **Extract**, **Update**, **Remove**, **Wire**, **Move**
- No trailing period
- Stay under 72 characters
- Body (optional): blank line after subject, then explain *why* not *what*

Avoid vague subjects like `UI clean up`, `updates`, or `misc fixes`. Each commit should be a complete thought.

## Branch Workflow

1. Branch from `main`.
2. Keep branches focused on one calculator or one logical concern.
3. Rebase onto `main` before opening a PR if your branch has diverged significantly — prefer rebase over merge commits on feature branches to keep history linear.
4. Delete the branch after merge.

## Pull Requests

- **Title:** match the final merge commit subject (imperative, ≤72 chars).
- **Body:** include a short description of what changed and why, plus a testing note (which commands to run, which Playground steps to verify).
- Target `main`.
- PRs must pass CI (Core Tests + Plugin Build & Playground Smoke Test) before merge.
- At least one approval required before merge.
- Use **squash merge** for small PRs (1–3 commits). Use **merge commit** for larger feature branches where individual commit history is meaningful.

## What Not to Commit

- Build artifacts (`dist/`, `build/`, `*.zip`) — these are generated by CI.
- `node_modules/` — already in `.gitignore`.
- `.env` files or any file containing secrets, API keys, or license keys.
- Editor-specific files not already covered by `.gitignore` (add them to your global gitignore instead).

## Tagging and Releases

Tags follow `v<major>.<minor>.<patch>` (semver). Only cut a tag from `main` after CI is green. Release notes live in the tag annotation or GitHub Release body.

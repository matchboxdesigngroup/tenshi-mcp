# Changelog

All notable changes to this project are documented in this file.
The format is based on [Keep a Changelog](https://keepachangelog.com/en/1.1.0/).

## [Unreleased]

### Added
- **Sensitive-file policy (#20, part of tenshi#13).** `src/policy/paths.js`: every path-reading tool checks the path against the site's mandatory allowlist (`allow.extensions`, `allow.directories`) and a built-in denylist that the registry cannot relax: hidden files and directories (`.env` and variants, `.git`, `.ssh`, `.htaccess`, ...), any name containing `wp-config`, any name containing `wp-config` or `wp.config`, editor backups, database, dump, backup, archive, key and certificate extensions anywhere in the name, credential and backup file names with any number of parts, any name containing `backup`, names with words such as `dump`, `bak` or `secrets`, directories such as `db-dumps/`, `bak/` and `old/`, and configuration files named for an environment (`local-config.php`, `db-config.php`, ...). For `read_log` only, the site's own name at the start of its log file names (a registry value) is skipped, so a site whose name contains a denied word keeps its logs. Names are compared after Unicode compatibility normalisation and lower-casing, with trailing dots and spaces removed. The policy runs on the normalised request before any connection and again on the canonical path the server resolved (a symlink with an allowed name to a denied file is refused).
- **Credential redaction (#20).** `src/policy/redact.js`: every line of returned content that looks like it carries a credential is replaced as a whole by `[redacted credential line]`: assignments of credential-like names in the common syntaxes (PHP constants and array keys, `var_dump` output, JSON, YAML, INI, environment files, XML elements), with a value on the next line or in a YAML block scalar; credential-like query-string parameters; any user information in a URL; `Bearer`/`Basic` values; command-line password options; prose such as "the password is"; cloud key ids, JSON web tokens and well-known token prefixes; private key blocks (also when the text starts inside one); base64 key bodies. Lines are classified on their whole text before any filter, selection or cut: `read_file` reads up to 4096 bytes past `maxBytes` so the line at the cut is judged on its whole text, and returns a redacted line only as the whole marker; `read_log` classifies the partial first line of its window before dropping it. So neither a filter nor the choice of `maxBytes` can be used to recover any part of a redacted line. Markers count toward `maxBytes`. Every rule is linear in the line length. Both tools return `redactedLines` (a count) and never the redacted text.
- Open-time checks (#20): after open, `fstat` must report the same type, permissions and owner as the `lstat` before it, and a second `realpath` must return the same canonical path; nothing is read from a handle that fails. A canonical root of `/` is refused.
- Lexical input rules (#20): paths with control or format characters (bidirectional overrides, zero-width characters, line separators), unpaired surrogates, backslashes, percent signs, or characters that become `.`, `/` or `\` under Unicode compatibility normalisation are refused before any connection.
- Tests (#20): `tests/redaction-cut.test.js` (for every `maxBytes` from 1 to the file length, no part of a credential is returned, for several secret shapes, also through the fake server; `read_log` windows that start inside an assignment or a key block), 1 MB hostile-line timing tests for every redaction rule, `tests/policy.test.js` (denylist variants, allowlist, redaction), `tests/confinement-policy.test.js` (fake-server fixtures: symlink out of the root, loop, swapped link, file and directory, hard links, traversal encodings, sensitive names, allowlist misses, doubled-slash `realpath` replies for root and target, redaction, refusals byte-identical to not found in the handler and over the MCP protocol), `tests/site.test.js`, and new cases in `tests/config.test.js` and `tests/confine.test.js`. The fake server supports owner and permission overrides, hard links (one node under two names) and one-shot hooks that change the tree between two requests.
- Read-only SFTP layer (#1): `src/ssh/sftp.js` gives tools a session facade with only `realpath`, `lstat`, open for reading, `fstat`, bounded `read` and `close`, under one 10-second deadline per call that closes the SFTP channel on expiry; `src/ssh/confine.js` confines paths lexically and then by SFTP `realpath` with path-segment comparison and a regular-file check; `src/errors.js` defines the fixed error codes.
- In-process SSH/SFTP server fake for unit tests (`tests/helpers/fake-sftp-server.js`, built on `ssh2`'s server mode, no new dependency) and tests against it: `tests/sftp.test.js`, `tests/confine.test.js`, `tests/errors.test.js`, `tests/boundaries.test.js`, `tests/refusal-order.test.js`. Tool tests fail if the fake receives any exec, shell or other non-SFTP request (#1).
- **Host-key pinning (#1).** Each server in the registry now requires `hostKeys`: one to five SHA-256 fingerprints in the OpenSSH form (`SHA256:<base64>`, as `ssh-keygen -lf` prints; the base64 may carry its `=` padding and is stored without). Every new connection, including each reconnect after the pool dropped one, passes `ssh2` `hostHash: 'sha256'` and a verifier (`src/ssh/host-key.js`, `hostVerifierFor` in `src/ssh/client.js`). The verifier compares the presented key with every pin in constant time, with no early exit, and rejects during the key exchange. A mismatch sends no authentication request and opens no SFTP channel. `hostVerifierFor` always returns a verifier; one for a server without valid pins rejects every key. There is no trust on first use, no environment override and no switch to skip the check. Mismatches are not logged.
- Fixed error code `E_HOST_KEY` for a host key that matches no pin. The message never contains a fingerprint, the host or a path (#1).
- Tests: `tests/host-key.test.js` (fingerprint form, constant-time comparison of every pin, fixed OpenSSH vectors in `tests/helpers/host-key-vectors.js`), `tests/host-key-pinning.test.js` (fake server: matching pins, rotation, mismatch refused before authentication, unpinned registry refused, reconnect re-verified behind a TCP forwarder) and `hostKeys` cases in `tests/config.test.js`. The fake server counts authentication attempts and exposes its host-key fingerprint (#1).
- `tests/server.test.js`: starts the server over stdio with the SDK client and checks the reported server name, the tool names and the deprecated-variable warning (#11).
- CI workflow (`.github/workflows/ci.yml`) on pull requests and pushes to `main`: `npm ci`, `npm test`, and an audit check, with actions pinned by commit SHA (#3).
- `.nvmrc` pinning Node 23 for local development and CI, matching the platform local development guide (#3).
- `npm run audit:check` (`scripts/audit-check.mjs`, Node built-ins only): runs `npm audit` online against the public registry with dev, optional and peer dependencies included regardless of `.npmrc`; fails on high or critical advisories not listed in `.audit-allowlist.json`, on advisories whose reported severity differs from their entry, on malformed, duplicate, expired or over-60-day entries, and on incomplete npm output. Unit tests in `tests/audit-check.test.js` (#3).
- `.audit-allowlist.json` with the high and critical advisories present on `main` when CI was added, expiring 2026-11-30; dependency updates tracked in #5.
- `CONTRIBUTING.md` with branching, commit, merge, PR, roles/models, and definition-of-done conventions.
- Issue templates (feature, bug, spike, manual test) and a pull request template.
- `servers.json.example` with placeholder values, referenced by the README and `CLAUDE.md`.
- Status note in `README.md` and `CLAUDE.md`: the tool layer is under security review.

### Changed
- **Breaking: the registry requires `allow` on every site (#20).** `allow.extensions` (1 to 50, a dot and 1 to 16 letters or digits, compared case-insensitively, never an always-denied extension) and `allow.directories` (1 to 50, relative paths matched by whole segment at any depth, `.` for the whole tree, never a denied directory). Site names must be host names and must not be `__proto__` or an `Object.prototype` property name (Zod's record silently dropped `__proto__` and kept `constructor` as a site); `wordpressRoot` and `logDir` must be absolute and canonical (one trailing slash allowed, never `/`, no control characters or backslashes). Any violation refuses the whole registry with a message that names the server and field, never the value. Migration: add `allow` to every site before upgrading; `servers.json.example` shows one.
- Site lookups use `Object.hasOwn` (`resolveServerForSite`, `getSiteConfig`) (#20).
- **`read_log` serves only the exact configured log path (#20).** A log that is a symlink, even to another file inside the root, or that sits under a symlinked directory, is refused; the configured root itself may still be a symlink. The denylist applies to log paths.
- **`read_file` no longer serves `wp-config.php`** or any other denied file, and serves only files the site's `allow` list covers. `bytes` now counts the returned (redacted) content (#20).
- Tool descriptions mention the policy and redaction. README, `CLAUDE.md`, ADR-002 and the implementation plan describe the policy, the redaction and the residuals (check-then-open race, undetectable hard links) (#20).
- **Breaking: the registry refuses to load without host-key pins (#1).** A server with no `hostKeys`, an empty list, more than five entries, a duplicate (after normalising) or an entry not in the `SHA256:<base64>` form (hex digests and MD5 or SHA1 fingerprints included) is a startup error. The error names the server id (or its position) and the field, never the value, and the whole registry is refused. A failed load also empties a registry loaded earlier. Registry validation errors are now `RegistryError` with that message instead of a raw Zod error. Migration: before upgrading, add `hostKeys` to every server, with fingerprints obtained out of band. `ssh-keyscan -p <port> <host> | ssh-keygen -lf -` lists what the server presents, and you must compare that with the provider console or the output of `ssh-keygen -lf` on the server's host-key file through a channel you already trust. The README section "Host-key pins" has the steps and the rotation procedure. `servers.json.example` shows a placeholder pin.
- **`read_log` reads over SFTP (#1).** It reads at most the last 256 KB of the configured log with one bounded read, applies the optional filter in this process as a case-insensitive literal substring (at most 200 characters; never a regular expression, never sent to the server), returns the last `lines` matches (cap 500), cuts lines longer than 2000 characters and caps the content at 51200 bytes. Log paths come from the registry only and get the same confinement as `read_file` (inside `wordpressRoot` for the debug log, inside `logDir` for error and access logs). Output: `resolvedPath` and `lineCount` are removed; `requestedLines`, `returnedLines` and `truncated` (`window`, `longLines`, `bytes`) are added.
- **`read_file` reads over SFTP (#1).** The relative path is checked lexically, then resolved with SFTP `realpath` and must lie strictly inside the canonical WordPress root by path segment; symlinks that leave the root, directories and other non-regular files are refused. At most `maxBytes` (cap 51200) are read. Output: `requestedPath` and `resolvedPath` are removed; `path` (canonical, relative to the root) and `bytes` are added; `truncated` is now exact (a file of exactly `maxBytes` is not flagged). `path` is limited to 1024 characters.
- Refusals that need no server (unknown or prototype site names, paths that leave the root lexically, registry log paths that leave their directory) are made in the tool before a connection is opened, so they open no SSH connection or SFTP session and return `E_NOT_AVAILABLE` even when the server is unreachable. A `realpath` reply that is not in canonical form is refused instead of being normalised. Cuts at the line and byte caps no longer split a character (#1).
- Tool errors are fixed codes (`E_NOT_AVAILABLE`, `E_INVALID_INPUT`, `E_TIMEOUT`, `E_REMOTE`, `E_INTERNAL`) and never contain the arguments, server paths or remote error text; unknown site, outside-root, missing and forbidden paths share `E_NOT_AVAILABLE` (#1).
- Connection pool: concurrent first calls to a server share one connection attempt, a connection that completes after the pool was closed is disposed, and a socket error after connect drops the pooled connection instead of reaching an emitter with no listener. The 5-minute idle timeout is unchanged (#1).
- README, `CLAUDE.md`, `docs/standards/code-review.md` and `tests/integration.js` describe the SFTP model; ADR-002 and the implementation plan carry a superseded-in-part note (#1).
- Audit gate hardening (#10, CI follow-ups from #4): `scripts/audit-check.mjs` now passes `--package-lock=true` and `--include=prod` to `npm audit`, so `package-lock=false` in an `.npmrc` or the environment can no longer make it audit a freshly resolved tree instead of the lockfile. Stale allowlist entries (advisory no longer reported at high or critical) now fail the job instead of only being printed. An entry's `severity` must now match the reported severity exactly: an advisory re-rated in either direction fails until the entry is updated (it previously failed only when re-rated upwards, so an entry recorded as `critical` covered a `high` advisory). An advisory with an unknown or missing severity always fails, even when its id and package are allowlisted as critical. A `null` or otherwise unexpected `via` item, or a vulnerability entry without a `via` list, fails closed with a message instead of being skipped. npm's top-level `message` (how npm 10 reports an unreachable registry) is printed first. The script also runs when invoked through a symlink (it compared the typed path with the module path and exited 0 without running). CI runs `node scripts/audit-check.mjs` directly instead of `npm run audit:check`, so `node_modules/.bin` cannot shadow `npm`, and runs it before `npm ci` and `npm test`, so no dependency code (install scripts or tests) runs before the audit; the job name `Install, test, audit` is unchanged (`docs/standards/git.md` and `code-review.md` describe the new order). CONTRIBUTING.md lists proxy and TLS settings from npm config as a known limit. `--strict-ssl=true` is forced as well, so `strict-ssl=false` in an `.npmrc` or the environment cannot make npm accept any TLS certificate. The allowlist entries are unchanged; only its `$comment` changed, to describe the stale rule and exact severity matching.
- Renamed the project to Tenshi-MCP (tenshi#3, #11): package name `tenshi-mcp` (package.json and lockfile root), MCP server name reported over the protocol `tenshi-mcp` (was `ssh-wp-tools`), registration key `tenshi-mcp` in `.mcp.json.example` and the README and `CLAUDE.md` examples, README and `CLAUDE.md` titles, and the implementation plan renamed to `docs/specs/2026-06-04-tenshi-mcp-server.md`. Tool names `read_log` and `read_file` are unchanged. The registration key is client-side configuration that the server never reads, so an existing registration under the old key keeps starting the server; rename it to match the docs.
- **Local configuration change (breaking in M5):** the registry path variable is now `TENSHI_MCP_SERVERS_PATH` (was `SSH_MCP_SERVERS_PATH`). The old name is still read as a deprecated fallback, see Deprecated. `.env.example` lists the new name and the old one only as a commented line.
- **`.mcp.json` is no longer tracked** (#11): it is now `.mcp.json.example` with placeholder paths, and `.mcp.json` is git-ignored. Pulling this change deletes the tracked `.mcp.json` from existing checkouts (if you changed it locally, copy it aside before pulling); recreate it with `cp .mcp.json.example .mcp.json` and set your absolute paths. README and `CLAUDE.md` describe registering the server in your MCP client configuration (for Claude Code, a project `.mcp.json`) instead of `.claude/settings.json`; the spec has a correction note.
- README, `CLAUDE.md` and `.env.example` now say that the server does not load `.env` files: `TENSHI_MCP_SERVERS_PATH` must be set in the environment of the process that starts the server (MCP client `env` block, shell `export` or inline). `.env.example` is a template only (#11).
- Example site domains, server ids and absolute paths in docs, tool descriptions and `tests/integration.js` are neutral placeholders (`example.com`, `example-server`, `/path/to/tenshi-mcp`).
- `CONTRIBUTING.md`, `CLAUDE.md`, and `docs/standards/` describe the CI checks and the audit allowlist; the "CI is being added" notes are removed (#3).
- `docs/standards/git.md`, `code-review.md`, and `shell.md` now describe this Node MCP server and the shared conventions (they were copied from an unrelated project).

### Deprecated
- `SSH_MCP_SERVERS_PATH`: read only when `TENSHI_MCP_SERVERS_PATH` is unset or empty (an empty or whitespace-only value counts as unset; other values are used verbatim, not trimmed), with a one-line startup warning on stderr that names the variables and never their values; when both are set the new name wins and the warning says the old one is ignored. Removed in M5 (#11).

### Removed
- `src/ssh/executor.js` (`runCommand`) and `tests/executor.test.js`: no tool runs a remote command or builds a command string (#1).
